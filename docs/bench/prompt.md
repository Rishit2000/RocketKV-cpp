# 执行 RocketKV 32K benchmark

你是本仓库的实验执行 agent。先读 `docs/bench/bench.md`，以其中的实验设置、表头和作图清单为准。请实际运行实验、保存原始记录、自动回填五张表并生成图，不要停在写脚本或提交运行命令。

## 1. 锁定配置，先验证再放量

- 从仓库根目录运行，复用现有评测环境和 `build/runner`。固定模型、F16 KV、压缩预算 1024、输入上限 32768、`n_ctx=33792`。从现有配置派生 32K 配置，不覆盖 8K 配置。记录 Git commit、二进制哈希、设备、线程数、配置和输入清单；原始结果放在 `results/bench32/`。
- 三组固定映射：`off` → **Full KV**；`stage1` → **Stage 1**；`hsa` → **Stage 1 + Stage 2**。没有独立 Stage 2 组。单机串行测量，不同时运行两个 GPU benchmark。
- 先用同一条输入走通三个模式，再做一次 32K 边界检查。核对实际 `prompt_tokens`、计时及 RSS。发生淘汰时验证 Metal Stage 1 捕获、主机捕获字节为零；HSA 确认 Metal 后端且 `stage2_layer_calls == model_layers * decode_forward_calls`。异常先定位，不以 CPU 回退或更短输入冒充成功。

## 2. 执行两组实验

| 实验 | 怎么跑 | 填哪张表 |
|---|---|---|
| LongBench 质量 | 使用 `scripts/run_longbench_stage2.py --mode all --stage1-backend metal --budget 1024`，显式传入 32K 配置和输出目录。先跑 ★ 四任务各 30 条，再跑 16 个任务全部样本；试跑和正式结果分目录。沿用各任务生成上限。 | 表 1 只填全量 `score_pct`；16 项齐全后再算等权宏平均。 |
| 延迟和内存 | 按 `bench.md` 固定 4 个 `multi_news` 输入，保存源 ID、构造方式及哈希。三组复用同一批输入和各档长度；拼接负载须在表和图中标明。5 个长度 × 4 个输入 × 3 个模式 × 3 次重复，共 **180 次有效测量**。轮换模式顺序，每次只跑一条，用 `/usr/bin/time -l` 直接包住 runner，同时采集四项指标。 | 表 2、3、4a、4b 来自同一批运行。逐次核对实际长度和 `decode_forward_calls == 32`；不要把提前 EOS 的短运行混入。 |

性能实验记录每次的输入 ID、长度、模式、重复编号、返回状态、runner JSON 和原始 RSS 日志。每个条件先取同一输入三次重复的中位数，再取四个输入的中位数。质量评测保持正常生成；性能评测如需固定 token 序列，三组须完全一致，关闭 logits trace，记录协议。

## 3. 长任务与 compact

每完成一个任务或长度档，持久化进度。**每当上下文已用比例达到约 30%（约剩 70%），立即保存检查点并主动 compact**，不等阶段结束，也不停止正在运行的实验。检查点放在 `results/bench32/progress.md`：记录已完成和缺失的组合、活跃进程或会话 ID、输出路径、失败原因、下一条命令。若当前工具不能主动 compact，保留同样的交接记录。恢复后先核对进程、manifest 和已有结果，只补缺项，不重复启动。不要把整份日志贴入上下文。
